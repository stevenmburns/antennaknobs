### Were the guard's steps done before the earlier runs? Partly — stated plainly.

Asked directly, so answered directly, and the honest answer is not a clean yes.

* **`b9bc3e2f0` (the 618-cell catalog run).** The checkout and the rebuild *were*
  done: momwire was put at `1ca8725` and rebuilt with `MOMWIRE_REQUIRE_ACCEL=1`,
  and `_accelerators_avx2` / `_near_interface_accel_avx2` were confirmed to
  import. So the code and the binaries were right, and the accelerator variant
  was the same AVX2 pair as today. **But the metadata check would have FAILED:**
  `importlib.metadata.version('momwire')` read **0.53.0** against a pyproject
  saying 0.55.0, because editable metadata does not follow a submodule checkout.
  That was observed at the time and not acted on. It is a metadata artefact and
  not a code one — refreshing the editable install just now, from the same
  checkout, reports 0.55.0 — but the check as specified did not pass, and the
  run predates the check existing in this form.
* **`CONFIRM-1532` (the 18-cell confirmation).** `make build` was **not** re-run
  for it. momwire's working tree had not moved from `1ca8725` since the rebuild
  above, so the `.so` files were built from exactly those sources; the submodule
  SHA and the two accelerator imports were verified, and the metadata again read
  0.53.0.
* **What I cannot show.** There is no build log or machine-readable artefact from
  either run — the evidence is this session's transcript, not a file. That is
  precisely the gap `verify_env.py` closes by writing the provenance into the
  records.

Either way, this re-run supersedes both for publication.

## The predicted-movement set, named before the run

Every cell is diffed against `b9bc3e2f0`'s records. Movement is predicted to be
confined to **7 of the 103 designs**, by three mechanisms read out of the diff
rather than guessed from issue titles. The set is committed as
`predicted-movement-set.json`.

**M1 — the vertex-only parity exemption (#1519).** `_parity_for_solver` now
consults `vertex_only_names(network)`, so a wire whose ports are all vertices
keeps its authored segment count instead of being coerced. Exactly one catalog
design has a `PortAtVertex`:

* `dipoles.invvee_apex` — all three engines may move.

**M2 — the coated-wire pair (#1523, merged as #1532).** The three designs that
default to a jacketed `wire_type`. **NEC-5 rows only**, and they are predicted to
equal `CONFIRM-1532`'s values *exactly*, since that run used the same AK tree
(`3b0d942a9`, byte-identical tree to `97ca2b6b0`) and the same momwire:

* `dipoles.pota_invvee`, `dipoles.invvee_catenary`, `wire.efhw_sloper`

**M3 — momwire's engine now meshes its network (#1527).** `MomwireEngine` gained
`self._network = self._network_as_meshed(network)` and
`splits_wire_at_feed = parity in ("odd", "even")`, so a wire whose ports are not
already sites of its own count is split. No catalog design uses a positioned port
(`at=` appears in zero designs) and no wire carries more than one port, so this
can only reach the designs whose port kinds are not plain centre gaps:

* `wire.sterba_bl` (16 × `PortAtEnd`)
* `arrays.bowtie1x2_bl`, `wire.doublet_balanced_tuner` (`PortOnWireFloating`)
* `dipoles.invvee_apex` again

**`PulseSolver`/`HarringtonSolver` gained parity "odd" in the same change and is
irrelevant here** — this study runs neither.

### Predictions

* **R1.** Every cell outside those 7 designs is **bit-identical** to
  `b9bc3e2f0`'s record — tested on the stored `[re, im]` pairs, not to a printed
  precision. Bar: zero movers among the other 96 designs.
* **R2.** The six jacketed NEC-5 rows equal `CONFIRM-1532`'s values exactly.
* **R3.** The bs2 and razor rows of the three jacketed designs are bit-identical
  to `b9bc3e2f0` (the jacket fix is in the NEC writers only).
* **R4.** At least one of the 7 predicted designs actually moves — a prediction
  that nothing moves anywhere would be satisfied by a harness that silently
  re-ran the old code, which is the failure this whole section exists to catch.

**Any moved row outside the predicted set is a finding**, and is reported with
its design and engine rather than absorbed.

**610 of 618 cells are bit-identical to `b9bc3e2f0`. All 8 movers are inside the
predicted set, and no row outside it moved.** The predicted set was 7 designs;
only 4 of them actually moved, which is the right direction for a prediction of
this shape — it was a bound on where movement could appear, and the bound held
with room.

What the two mechanisms did:

* **M1, the vertex-only parity exemption.** `dipoles.invvee_apex`'s **bs2** rows
  moved, by 0.0128 % and 0.0146 %. Its razor-2p and NEC-5 rows did not move at
  all — both already declare even parity and the apex wire's authored count is
  even, so the exemption changes nothing for them. This is the smallest movement
  in the run and it is a mesh change, not a physics change.
* **M2, the coated-wire pair.** The six jacketed NEC-5 rows moved by 10.5–14.3 %
  and land exactly on `CONFIRM-1532`'s values. Their bs2 and razor-2p rows are
  untouched, which is what a change confined to the NEC writers should do.
* **M3 did not fire.** `wire.sterba_bl`, `arrays.bowtie1x2_bl` and
  `wire.doublet_balanced_tuner` are bit-identical on all three engines.
  `_network_as_meshed` reaching the momwire engine changed no catalog answer:
  every catalog port is either a plain centre gap or sits somewhere the new
  meshing agrees with the old. Predicting these three was the conservative call
  and it cost nothing.

The one number worth carrying forward: **razor-2p's widest disagreement with
NEC-5 over the whole catalog is now 2 %**, on `verticals.four_square` over
Sommerfeld, against 14.4 % before #1532. The 5–14 % tail that dominated the
original study is gone from main, and what remains at the top of that
distribution is the Sommerfeld ground-model residue AK#1516 measured separately —
it does not shrink under mesh refinement.
