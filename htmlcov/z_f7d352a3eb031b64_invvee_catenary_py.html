1"""Inverted-vee dipole whose arms hang as real catenaries (issue #698, unit 2). 

2 

3Every other inv-vee in the catalog (`dipoles.invvee`) treats an arm as a 

4straight chord at a fixed droop angle. A real wire does not do that: strung 

5from the apex to a stake under some rope tension, it sags into the shape 

6`antennaknobs.catenary` solves for — a hanging-chain equilibrium set by the 

7wire's own weight per metre and how hard the halyard pulls. This design wires 

8that solve into the geometry: `build_wires()` emits each arm as a chord 

9polyline sampled uniformly along the solved catenary's arc length, following 

10the `specialty.faceted_helix` curved-wire idiom (`Wire(p_i, p_{i+1}, 

11n_seg=None)`, `auto_mesh` owning the electrical density — issue #630's 

12lesson: never hand-freeze `n_seg` on a chorded curve). 

13 

14Two rig models share the same wire and geometry idiom, picked by `rig_model`; 

15`rig_solutions()` is the single method that solves either one, and 

16`rig_report()` (issue #698 unit 3) reports the tension/sag readout for 

17whichever model is active. 

18 

19Model 1 — tensioned halyard (catenary's "model 1", the default) 

20----------------------------------------------------------------- 

21Each arm is `catenary.solve_tensioned`: a wire of *fixed cut length* 

22`0.25 * design_wavelength * length_factor` — the same length law 

23`dipoles.invvee` uses for its straight arm — hangs from the apex, and its far 

24end is held by a massless rope of specified tension `tension_n` running to a 

25fixed stake. The wire's end position is not an input; equilibrium places it, 

26which is the whole point of the model: `tension_n` is the design knob and the 

27arm's droop is the answer. 

28 

29This keeps the **electrical knob and the mechanical knob orthogonal by 

30construction** — `length_factor` sets how much wire is up there; 

31`tension_n` sets how it hangs. Scrubbing tension never changes the cut 

32length, only the shape, exactly as issue #698 requires ("the electrical 

33knob must not move when tension changes"). As `tension_n -> infinity` the 

34arm's shape converges to the straight chord from the apex toward the stake, 

35which is the design's own built-in regression oracle against a straight-arm 

36inv-vee of the same geometry (see `tests/test_invvee_catenary.py`). 

37 

38Feasibility: the stake must be beyond the arm 

39---------------------------------------------- 

40`solve_tensioned` requires the stake to be farther from the apex than the 

41wire is long — a taut wire reaching for a stake it has already overshot has 

42no equilibrium at any tension. With the apex at `(0, base)` and the stake at 

43`(stake_dist, stake_height)` in the arm's own vertical plane, this needs 

44 

45 hypot(stake_dist, base - stake_height) > 0.25 * design_wavelength * length_factor 

46 

47The stock `stake_dist` (11.5 m, ~4.7x the default arm length — a realistic 

48guyed-inv-vee footprint that hangs the chord at ~33 degrees from horizontal 

49at the stock 1.0 N tension) and `stake_height` (1.0 m) satisfy this with a 

50huge margin even at the top of the `length_factor` UI range; nearly all the 

51reach comes from the horizontal offset — see the module tests for the 

52numeric check. Push the knobs hard enough (a very long 

53arm, a stake dragged close to directly under the apex) and the solver's own 

54`ValueError` explains exactly why no rig exists; this design does not 

55second-guess or clamp that error. 

56 

57Model 2 — anchored heavy rope (catenary's "model 2") 

58------------------------------------------------------ 

59Each arm is `catenary.solve_anchored`: the SAME fixed-cut-length antenna 

60wire (same `WireSpec` weight as model 1), followed by a second chain segment 

61— a rope of its own length and weight, `rope_weight_g_per_m` — whose far end 

62must land exactly on a fixed **ground anchor**. That anchor reuses 

63`stake_dist` / `stake_height`, the same rig-point params model 1 calls a 

64"stake": for this model they name where the rope is staked to the ground, 

65not a pull direction. 

66 

67Fixed endpoints plus two inextensible fixed lengths leave **no tension 

68freedom** — `tension_n` is ignored entirely in this model. The knob a winch 

69actually turns is the rope's take-up, which raises the apex tension and 

70lowers the sag as an **output**, not an input; `rig_report()` is where that 

71readout surfaces (issue #698's "tension readout in N and lbf; sag reported" 

72acceptance criterion, plus the derived `rope_length_m` — what you'd actually 

73cut). 

74 

75The knob is SLACK, not absolute rope length 

76---------------------------------------------- 

77`rope_slack_mm` — not a rope length — is the UI knob, for a reason a first 

78pass at this design got wrong (an absolute `rope_length_m` knob failed 

79review): the rope's cut length is derived inside `rig_solutions()` from the 

80CURRENT geometry, not stored as its own param — 

81 

82 reach = hypot(stake_dist - EPS, base - stake_height) # apex -> anchor 

83 rope_length_m = (reach - arm_length_m) + rope_slack_mm * 1.0e-3 

84 

85An absolute `rope_length_m` param cannot span the geometry knobs' own 

86ranges: `reach - arm_length_m` (the shortest rope that can possibly reach) 

87moves with `length_factor`, `stake_dist`, and `stake_height`, so any single 

88fixed length is infeasible across large parts of their sliders — scrub 

89`length_factor` to its 0.8 UI minimum, or `stake_dist` to its 6.0 UI 

90maximum, and a `rope_length_m` picked for the stock geometry raises "chain 

91cannot reach the anchor" for every value in a reasonably sized UI range. 

92Slack is feasible **by construction** instead: the total chain arc is always 

93`reach + rope_slack_mm * 1e-3`, strictly more than `reach`, for every 

94positive slack and every combination of the geometry knobs — the one 

95remaining way to fail is `reach <= arm_length_m` (the wire ALONE already 

96reaches past the anchor, so no rope length, slack or otherwise, rescues it); 

97`rig_solutions()` raises a `ValueError` naming that constraint rather than 

98clamping it away. It does not occur anywhere in the tested UI cross-product 

99(`length_factor` in `{0.8, 1.25}` x `stake_dist` in `{1.0, 15.0}` x 

100`stake_height` in `{0, 3}`, all eight corners, at stock `base`) — see the 

101module tests — but a knob combination well outside those ranges (a stake 

102dragged nearly under the apex, or a very long arm) can still reach it. 

103 

104This also turns the taut-limit's hypersensitivity from a liability into the 

105slider's whole point: at the stock geometry the shortest feasible rope is 

106~10.5 m of arc (the 33-degree stake sits ~13 m of reach from the apex), and 

107(per the shallow-catenary relation `H ~ w*L^2/(8*sag)`) apex tension falls 

108off steeply as slack grows — not a numerical artifact, the ordinary 

109behaviour of any lightly loaded near-taut catenary (see `catenary.py`'s own 

110numerics discussion). `rope_slack_mm`'s range (0.05-200.0 mm) puts that 

111whole taut-to-slack transition inside one slider: its low end is a 

112hand-tensioned halyard's tens-of-newtons regime, its high end a visibly 

113saggy rope carrying almost nothing. The stock default, 0.5 mm of slack, 

114lands the stock apex tension at ~22.5 N — inside a real halyard's range 

115without sitting at either the reach floor or the slider's own edge. 

116 

117Neither `tension_n` nor `rope_slack_mm` / `rope_weight_g_per_m` is hidden 

118from the UI even though only one set is "live" per `rig_model`: the 

119`ui_params` `hidden` hint (see `dipoles.invvee`'s `angle_deg` or 

120`wire.doublet_ladder_tuner`) is an unconditional, per-param override applied 

121once at schema-derivation time — it cannot key off another param's value, so 

122there is no way to hide `tension_n` only when `rig_model == "anchored_rope"`. 

123Both knobs stay visible; this docstring (and each param's own comment below) 

124says which one is live in which model. 

125 

126Geometry 

127-------- 

128The apex sits on the mast at `(0, 0, base)`. A short feed wire (the 

129`doublet_ladder_tuner` / `invvee` idiom: `eps = 0.05` m either side of 

130centre) carries the driven gap; each catenary arm starts from that feed 

131wire's end and runs in the +y or -y azimuth (no azimuth knob in this unit — 

132the two arms are always 180 deg apart). The catenary solve itself works in 

133the arm's 2-D vertical plane (`horizontal`, `z`); the design maps 

134`horizontal -> +-y` and holds `x = 0`. 

135 

136Requires a real `WireSpec`: a weightless wire has no catenary 

137(`solve_tensioned` raises `ValueError` for `wire_weight_n_per_m <= 0`, and 

138this module raises its own clear error first if `build_wire_material()` 

139returns `None`). The stock wire is `18-awg-pvc` (via `wire_type`), which 

140carries a real `weight_g_per_m` — swap the catalog entry and the antenna 

141sags differently AND its loss/insulation electrical behaviour changes in one 

142move (the same one-knob-two-effects story as `dipoles.pota_invvee`, issue 

143#316). 

144 

145`chords_per_arm` (default 14) is the *geometric* fidelity knob, independent 

146of the electrical mesh: it is passed straight through as 

147`samples_per_segment = chords_per_arm + 1` to the active model's solve, so 

148the solver's own uniform-in-arc-length sampling IS the chord split. 

149 

150`build_wires()` emits ONLY the wire segment's chords as antenna geometry — 

151`ChainSolution.segments[0].points` is always the wire, in both models. Under 

152`rig_model="anchored_rope"` the rope is a second chain segment, but it is 

153rigging, not a conductor: its shape is `rig_report()` diagnostics only and 

154never reaches `build_wires()`, so the wire count emitted is identical 

155between the two models. 

156 

157See also 

158-------- 

159`antennaknobs.catenary` for the chain solver and its numerics/sign 

160conventions; `dipoles.invvee` for the base design and param conventions; 

161`specialty.faceted_helix` for the chord-polyline-as-geometry precedent. 

162Issue #698. 

163"""

191def _tension_row(label: str, newtons: float) -> dict: 

192 """One tension readout row carrying BOTH units in a single string value 

193 ("22.5 N (5.06 lbf)"): issue #698's acceptance criterion asks for newtons 

194 and pounds-force, and a rigger reads them together — two numeric rows 

195 would double the height of a HUD that floats over the canvas, and a 

196 "lbf" row alone reads as a different measurement rather than the same 

197 one restated. The row is pre-formatted here because unit choice is the 

198 server's job in this contract (the frontend prints strings verbatim)."""

200 return { 

201 "label": label, 

202 "value": f"{n:.4g} N ({n / _N_PER_LBF:.3g} lbf)", 

203 "unit": None, 

204 "group": _RIG_GROUP, 

205 }

336 def rig_solutions(self) -> ChainSolution: 

337 """Solve one arm's catenary (both arms are mirror images in y, so 

338 one solve in the shared vertical plane covers both) under whichever 

339 `rig_model` is selected. Single source of truth for both models — 

340 `build_wires()` and `rig_report()` both call this same method, so the 

341 rigged shape and any diagnostics a caller reads off it (sag, 

342 tension, arc length) can never drift apart, and the two models can 

343 never disagree about the wire segment. 

344 """ 

345 spec = self.build_wire_material() 

346 if spec is None or not spec.weight_g_per_m: 

347 raise ValueError( 

348 f"{type(self).__name__}: catenary sag needs a real WireSpec " 

349 "with weight_g_per_m > 0 (a weightless wire has no " 

350 f"catenary); got {spec!r} from build_wire_material() — set " 

351 "wire_type to a catalog entry such as '18-awg-pvc'." 

352 ) 

353 

354 arm_length_m = 0.25 * self.design_wavelength * self.length_factor 

355 wire_weight = weight_n_per_m(spec.weight_g_per_m) 

356 apex = (_EPS, self.base) 

357 samples_per_segment = int(self.chords_per_arm) + 1 

358 

359 if self.rig_model == "anchored_rope": 

360 anchor = (self.stake_dist, self.stake_height) 

361 reach = math.hypot(anchor[0] - apex[0], anchor[1] - apex[1]) 

362 if reach <= arm_length_m: 

363 raise ValueError( 

364 f"{type(self).__name__}: the wire alone (arc length " 

365 f"{arm_length_m:.6g} m) already reaches past the anchor " 

366 f"(straight-line distance {reach:.6g} m) -- no rope " 

367 "length, slack or otherwise, can rescue this; move the " 

368 "anchor farther out (larger stake_dist / lower " 

369 "stake_height) or shorten the arm (smaller " 

370 "length_factor)." 

371 ) 

372 # SLACK is the knob, not the rope's cut length (issue #698 unit 

373 # 3 review fix): the cut length is derived from the CURRENT 

374 # geometry every solve, never stored as its own param, so it is 

375 # feasible by construction for every combination of the 

376 # geometry knobs above -- see the module docstring's "knob is 

377 # slack" section. 

378 rope_length_m = reach - arm_length_m + self.rope_slack_mm * 1.0e-3 

379 rope_weight = weight_n_per_m(self.rope_weight_g_per_m) 

380 segments = ( 

381 ChainSegment( 

382 length_m=arm_length_m, 

383 weight_n_per_m=wire_weight, 

384 name="invvee_catenary_arm", 

385 ), 

386 ChainSegment( 

387 length_m=rope_length_m, 

388 weight_n_per_m=rope_weight, 

389 name="rope", 

390 ), 

391 ) 

392 return solve_anchored( 

393 apex=apex, 

394 segments=segments, 

395 anchor=anchor, 

396 samples_per_segment=samples_per_segment, 

397 ) 

398 

399 if self.rig_model != "halyard": 

400 raise ValueError( 

401 f"{type(self).__name__}: unknown rig_model {self.rig_model!r}; " 

402 "expected 'halyard' or 'anchored_rope'" 

403 ) 

404 

405 return solve_tensioned( 

406 apex=apex, 

407 wire_length_m=arm_length_m, 

408 wire_weight_n_per_m=wire_weight, 

409 stake=(self.stake_dist, self.stake_height), 

410 rope_tension_n=self.tension_n, 

411 samples_per_segment=samples_per_segment, 

412 name="invvee_catenary_arm", 

413 )

415 def rig_report(self) -> dict: 

416 """Tension/sag readout for whichever `rig_model` is active (issue 

417 #698's "tension readout in N and lbf; sag reported" acceptance 

418 criterion) — the same shape for both models so a caller (the web 

419 adapter's solve response, issue #318's `wire_length_m` precedent) 

420 never has to branch on which model produced it. 

421 

422 `wire_end_height_m` is the z coordinate of the wire segment's own 

423 far end — the wire/rope junction under "anchored_rope", or simply 

424 the wire's end (there is nothing downstream of it) under "halyard". 

425 `rope_sag_m` / `rope_length_m` are `None` under "halyard" (there is 

426 no rope segment there — model 1's rope is massless and its length is 

427 never solved for, only its direction). Under "anchored_rope", 

428 `rope_length_m` is the CUT length `rig_solutions()` derived from 

429 `rope_slack_mm` and the current geometry — what you would actually 

430 cut and tie off, read back off the already-solved chain rather than 

431 recomputed (so it can never drift from what was actually solved). 

432 """ 

433 solution = self.rig_solutions() 

434 wire_seg = solution.segments[0] 

435 rope_seg = solution.segments[1] if len(solution.segments) > 1 else None 

436 apex_tension_n = solution.apex_tension 

437 end_tension_n = solution.end_tension 

438 return { 

439 "rig_model": self.rig_model, 

440 "apex_tension_n": apex_tension_n, 

441 "apex_tension_lbf": apex_tension_n / _N_PER_LBF, 

442 "end_tension_n": end_tension_n, 

443 "end_tension_lbf": end_tension_n / _N_PER_LBF, 

444 "horizontal_tension_n": solution.horizontal_tension_n, 

445 "wire_sag_m": wire_seg.max_sag_m, 

446 "rope_sag_m": rope_seg.max_sag_m if rope_seg is not None else None, 

447 "rope_length_m": rope_seg.arc_length_m if rope_seg is not None else None, 

448 "wire_end_height_m": float(wire_seg.points[-1][1]), 

449 }

451 def readout_rows(self) -> list[dict]: 

452 """Workbench readout rows (issue #712): the same numbers `rig_report()` 

453 returns, re-expressed as the generic self-describing row list the web 

454 adapter surfaces under "readouts" and the frontend renders with no 

455 design-specific code — `{label, value, unit, group}` per row, where 

456 `value` is a number the client formats, a short string it prints 

457 verbatim, or None (an em-dash). 

458 

459 `rig_report()` stays the machine-readable dict (its keys are a 

460 response contract of their own); this method is the *display* 

461 projection of it, so the two can disagree about presentation — 

462 millimetres instead of metres for a sub-metre sag, one combined 

463 "N (lbf)" string instead of two keys — without either one bending to 

464 the other's audience. It is called once, and only rows that mean 

465 something for the active `rig_model` are emitted (the rope rows exist 

466 only under "anchored_rope"), which is exactly the freedom the dict's 

467 fixed-key shape does not have. 

468 """ 

469 r = self.rig_report() 

470 rows: list[dict] = [ 

471 { 

472 "label": "rig model", 

473 "value": str(r["rig_model"]), 

474 "unit": None, 

475 "group": _RIG_GROUP, 

476 }, 

477 _tension_row("apex tension", r["apex_tension_n"]), 

478 _tension_row("end tension", r["end_tension_n"]), 

479 { 

480 "label": "horizontal tension", 

481 "value": float(r["horizontal_tension_n"]), 

482 "unit": "N", 

483 "group": _RIG_GROUP, 

484 }, 

485 _length_row("wire sag", r["wire_sag_m"]), 

486 ] 

487 if r["rope_sag_m"] is not None: 

488 # Model 2 only: model 1's rope is massless and never solved, so 

489 # a "rope sag: —" row there would imply a number that does not 

490 # exist rather than one that is merely missing. 

491 rows.append(_length_row("rope sag", r["rope_sag_m"])) 

492 if r["rope_length_m"] is not None: 

493 rows.append(_length_row("rope cut length", r["rope_length_m"])) 

494 rows.append(_length_row("wire end height", r["wire_end_height_m"])) 

495 return rows 

496 

497 # build_wire_material() is intentionally NOT overridden: the inherited 

498 # AntennaBuilder default already resolves a `wire_type` param via 

499 # `wire_from_catalog` (the same mechanism `dipoles.pota_invvee` relies 

500 # on), and the stock `wire_type` above already names a real WireSpec. 

501 

502 def build_wires(self): 

503 b = self.base 

504 solution = self.rig_solutions() 

505 # (horizontal, z) samples, uniform in arc length, apex-first. 

506 plane_points = solution.segments[0].points 

507 

508 wires = [ 

509 # Driven gap at the apex — the invvee/doublet_ladder_tuner 

510 # idiom: a short wire from -eps to +eps carries the excitation, 

511 # and each catenary arm starts from one of its ends. 

512 Wire((0.0, -_EPS, b), (0.0, _EPS, b), ex=1 + 0j), 

513 ] 

514 for sign in (1.0, -1.0): 

515 arm_points = [(0.0, sign * h, z) for h, z in plane_points] 

516 wires.extend(Wire(p0, p1) for p0, p1 in itertools.pairwise(arm_points)) 

517 return wires
